## Findings

### M1 (Major): the ends along a box's bottom are spread in the order the flows are written, so two back-flows that meet at one box can share a line silently, and an outer and an inner one from the same box cross
- Evidence: one lane, steps `s1`..`s5` chained forward.
  - Shared line, no report: `{from: 's5', to: 's3:bottom', label: 'Q'}` written before `{from: 's3', to: 's1:bottom', label: 'P'}`. Both run at y=138. The first goes from x=842 to 512 (it arrives at `s3:bottom@0.33`). The second goes from 555 (it leaves `s3:bottom@0.67`) to 225. On 512-555 the two lines lie on top of each other, so the figure reads as one line from `s5` to `s1` with two stubs at `s3`. `problems` and `warnings` are both empty. The unlabelled pair does the same at y=132. Written in the other order, the same two flows are drawn correctly (512 and 555 swap, so the legs do not touch). There are two causes. The overlap test in lib/dsl/swimlane.ts:149 is strict (`lo < ohi && olo < hi`), so spans that touch at one column get the same level. And `spread()` (lib/dsl/swimlane.ts:157-163) hands out the slots in the order the flows were declared. `edgeStats` skips pairs that share an end id, so the overlap is never counted.
  - Avoidable crossing, with a fix hint that does not work: `{from: 's5', to: 's1:bottom', label: 'Redo'}` written before `{from: 's5', to: 's3:bottom', label: 'Fix'}`. The outer one (deeper, y=166) leaves at `s5:bottom@0.33` (x=821). The inner one leaves at `@0.67` (x=864) and turns left at y=138 through the outer one's vertical leg. `edge-crossings` warns and says to change a target or merge the two into one flow. Writing the two flows in the other order removes the crossing. The same happens with `span: 2` steps (`s4 -> s1`, then `s4 -> s3:bottom`), and with two back-flows into one target (`s3 -> s1:bottom`, then `s5 -> s1:bottom`).
- Fix: at each `:bottom` end, give the slots by route, not by the order written. At a start box, the deeper flow takes the slot farther from its target. At a target box, the deeper flow takes the outer slot. At a box where one flow arrives and another leaves, the one going left takes the left slot. Alternatively, count spans that touch as overlapping (`<=`). Add a test for each order of the two cases above.

### M2 (Major): a hand-over that leaves a box in the middle runs through the back-flow's chip, and with a label the two chips sit on each other, but `check` only gives the generic crossing warning
- Evidence: lanes `a`, `b`, `c`. `s1`..`s5` in `b`, chained forward, with `{from: 's5', to: 's1:bottom', label: 'Again'}` and a hand-over `{from: 's3', to: 'c3'}` (`c3` in lane `c`, col 3). The back-flow chip is centred on the span (`labelAt` 0.5, `[507.8,126,52.4,24]`), and `s3`'s bottom is at x=534, so the hand-over's vertical line runs through the middle of the chip. With `label: 'Pass'` on the hand-over, its chip is `[511.4,132,45.2,24]`, which covers almost all of the other chip. `problems` is empty. The only warning is `edge-crossings`, which says the crossing cannot be removed with `dip` and suggests a different target. It says nothing about the labels. The crossing of the lines cannot be avoided, but the place of the chip can. A step in the middle that hands work to another lane, plus a way back from the end to the start, is the usual shape of a swimlane.
- Fix: put the under-flow's chip on a stretch of its horizontal leg that no other flow's vertical leg crosses (move `labelAt` off the x of the other lines' legs). Otherwise report label-on-label overlap as a problem. Add a test with this case.

### m1 (Minor): if the bands go through JSON before layout, the shared `under.rows` reference breaks, and the layout silently falls back to the old shared depth
- Evidence: I checked every path in the repo that copies the spec before layout, and none of them breaks the reference. `cloneData` (lib/core.ts:149, lib/spec-selective.ts:97, lib/legacy-core.ts:65, lib/dsl/diagram.ts:114) copies an object it meets twice only once. `copyBand` / `rewrite` are shallow. The JSON spec and MCP path builds the bands with `swimlane()` in the same process (`renderSpec` on a JSON-parsed spec draws 166/138). `structuredClone` keeps the sharing. pptx works from the laid-out figure, and the present thread posts only rendered output. Rendering the same bands twice, in parallel at two widths (`Promise.all`), and in two figures one after the other all gave correct depths. Nothing accumulates, because `off` is fixed when the bands are built and each render lays out its own copy. But `JSON.parse(JSON.stringify(bands))`, or a `structuredClone` of the swimlane band alone, makes `rows[group]` undefined. `resolveConnect` (lib/layout-connect.ts:223-224) then keeps the default `dip: 32` from the end boxes, and `layoutConnect` still reserves nothing (`under` survives). The nested pair then lands on one line at y=157 with the chips on each other, and the only report is the `edge-crossings` warning. With a tall middle box, the path and label overlap it (this one is reported).
- Fix: when `band.under` is set but its row is missing, throw an error that names the cause. Better, carry plain data (lane, row, step ids) and read the row bottom from `ctx.anchors` when the flow is resolved, so no shared mutable object is needed.

### m2 (Minor): no test covers `bendOffset` given without `bend`
- Evidence: the mutation `const plain = f.bend === undefined` (it ignores `bendOffset`) leaves all 11 tests passing. The behaviour is correct: `{from: 'r', to: 'p:bottom', bendOffset: 10}` stays elbow.
- Fix: add that case to the "explicit start side, or an explicit bend" test.

### n1 (nit): the part description says only part of the rule
- Evidence: lib/spec-parts/swimlane.ts:8 says "the lane grows for its label; a `bend` keeps the elbow". The lane also grows for stacked back-flows without labels. `bendOffset` and an explicit start side other than bottom keep the elbow too. The DSL header says all of this correctly.
- Fix: "(the lane grows to hold them; `bend`, `bendOffset` or a start side other than bottom keeps the elbow)".
