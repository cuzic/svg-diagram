# ADR 0053: 因果の図の配置探索を、結果を変えずに速くする

- 状態: 実装済み
- 日付: 2026-11-10
- 基点: `feat/json-spec`(JSON の入口 `svg-diagram/spec`、`svg-diagram/spec/edge` まで)
- 関連: ADR 0010(幅に収める)、ADR 0016(矢印の経路)、ADR 0019 D4(書く順を変えて探す)

## 背景

JSON の入口を Cloudflare Workers(1 リクエストの CPU は既定 30 秒、設定で 5 秒)で動かすと、40 ノード 60 リンクの `causeTree` に 8〜10 秒かかった。収まらずにエラーになる図は 14 秒かかった。

1 回の配置は 30〜50ms で、遅いのは回数だった。プロファイルで分かったこと:

1. 書く順を変えて交差を減らす探索(ADR 0019 D4)が、候補ごとに配置・経路・交差の数え上げまでを丸ごとやり直していた(228 回)。
2. その候補ごとに、ノード幅 200→160→130→110 と折り返し 4 通りを最初から試していた。基準と幅や折り返しが違う候補は、比較の段階で必ず捨てられる。
3. 経路の局所探索(ADR 0016)が、候補の経路を 1 本試すたびに、図全体の交差を数え直していた。
4. 矢印の並走を離す処理(ADR 0016 D14)が、候補ごとに全矢印の全線分を総当たりで比べていた。
5. 幅に収まらない試行(捨てられる)にも、並走の解消など経路の後処理をしていた。

## 決定

- D1. 経路の採点を差分で数える(`rescore`)。変わった経路だけを、他と自分同士で数え直す。数は数え直したときと同じ(テストで確かめる)。`crossingsWith` も、他の経路同士を数えない形にした。
- D2. 順序の探索では、候補を基準と同じノード幅と折り返しで 1 回だけ配置する(`planFit` の `sameFit`)。違う幅や折り返しの候補は、これまでも比較で捨てていた。
- D3. 順序の候補を、配置する前に層の間の交差数(`orderCrossings`、`layoutLayered` の順序決めだけ)で見積もり、いまの最良より多い候補は配置しない。ただし AND の矢印の交差は経路を引くまで分からないので、AND の矢印が交差している間は見積もりで候補を飛ばさない。
- D4. 並走の判定(`runsTogether` は同じ向きで 4px 未満)のために、線分を向きと横方向の座標の 4px 区画で引ける索引にした。近くの区画だけを比べる。
- D5. 幅に収まらない試行では、経路の後処理(D11 の共有、D14 の移動)をしない。収まらない試行から読まれるのは幅と層(エラーメッセージ)だけ。

## 結果

| 図 | 前 | 後 |
|---|---|---|
| 40 ノード 60 リンク(交差の多いランダムな CRT) | 10.7 秒 | 1.5 秒 |
| 40 ノード 45 リンク・AND あり、幅に収まらずエラー | 4.3〜14 秒 | 0.8〜1.5 秒 |
| 実務的な 11 ノードの CRT(Workers) | 114ms | 変わらず |

`examples/` の 196 枚の SVG は、変更の前後で 1 バイトも変わらない(D1〜D5 の各段階で比べた)。

## JSON の入口の上限

40 ノードで AND の矢印が多い CRT は、探索(AND が交差している間は見積もりで候補を飛ばさない)が残り、Workers で 4.5 秒かかった。`svg-diagram/spec` の `causeTree` は 30 ノード・45 リンクまでにした(`MAX_CAUSE_NODES`、`MAX_CAUSE_LINKS`)。実務の CRT は 10〜20 ノードほど。DSL の `causeTree()` には上限を設けない。

## 採らなかったこと

- 交差の数え上げを掃引法(O(n log n))にする。旧実装と同じ数を返したが、1 回に渡る線が少なく、呼び出し回数が多いので速くならなかった。差し戻した。
- 層ごとの並びを、隣の層を固定したビット DP で厳密に解く。結果(図)が変わるので、今回は入れない。見積もり(D3)の質を上げる手段として残す。
