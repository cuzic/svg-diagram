# ADR 0072: 指摘と図の部品に、ソースの位置(ファイル・行・桁)を持たせる

- 状態: 起草(2026-11-21)
- 基点: `main`(950584b、PR #398 まで)
- 関連: ADR 0013(失敗の伝え方)、ADR 0025/0026(検査の重大度)、ADR 0034(SVG の `data-node`)、ADR 0045(ブラウザの入口)、ADR 0071(JSON Schema)、svg-diagram-vscode(VS Code 拡張。Phase 2)

## 背景

VS Code 拡張は `check --format json` の指摘をエディタの波線にしている。指摘がソースのどこのことかを、CLI はほとんど言わない。

コードで確かめたこと(`check-diagram.ts`、`lib/rules.ts`、`lib/verify*.ts`):

- `line` を持つのは文書の検査(`doc-*`)と `--covers` だけ。図のソースの指摘には位置がない。
- 規則の指摘(`Finding`)は、部品をラベルで言う(`data.band` は `band.name` やタイトル)。拡張は、そのラベルを引用符つきでソースの文字列から探し、最初に見つかった所に置く。同じ文言が 2 か所にあると外れ、組み立てた文字列では見つからない(1 行目に置く)。
- レイアウトの誤り(`verdict.problems`)はただの文字列(`"A" overlaps "B" by 12x4px`)で、部品への参照がない。
- ソースの読み込みや `define()` で投げた誤り(`build-error`)は、0.8.0 から JSON で出る。メッセージだけで行がない。0.5.0 は JSON を出さずに落ち、拡張はスタックの行を読んでいた。そのため 0.8.0 に上げると、誤りが 1 行目に移った(拡張の README に書いた後退)。
- SVG は平らな図形の並び。どの図形がどの部品かは、`data-node`(ADR 0034、id のある節だけ、希望したときだけ)でしか分からない。プレビューで図をクリックしてソースへ飛ぶ手がかりがない。

確かめた前提(U0 の試し。scratch で Node 26.13、`engines` は `>=22.18`):

- `.ts` のソースは Node の型の取り除き(type stripping)で読まれる。型は空白に置き換わるので、スタックの行・桁はソースのとおり(`t.ts:7:3` を確かめた)。source map は要らない。
- `Error.captureStackTrace` は 1 回 約 1 µs(整形しなければ)、整形しても約 3 µs。部品が数百あっても 1 ms に届かない。
- レイアウトは部品を `{...band, x, y, …}` で写す(`lib/layout-handlers.ts`、`lib/layout-connect.ts`)。`cloneBand` / `mapBands` も、記述子を写すか spread する。spread は列挙できるシンボルのキーも写す。`JSON.stringify` と `Object.keys` はシンボルのキーを見ない。

## 決定

**D1. 位置は `{file, line, column}`。** `line` と `column` は 1 始まり(エディタや SARIF と同じ)。`file` は `check` の `file` と同じく、カレントディレクトリからの相対パス。粒度は**部品を作った呼び出し 1 つ**: `box(...)`・`cycle([...], ...)`・`connect(...)` / `.connect(...)`・`diagram(...)`。部品の中に書いた項目(`cycle` の各 `{label}` など)は、別の位置を持たない。項目まで絞るのは拡張の仕事で、部品の呼び出しの範囲の中でラベルを探す(今の「ファイル全体から探す」より外れにくい)。

**D2. 取り方: 公開の入口で、部品を作る関数に一度だけ包みをかぶせる。**
- `lib/dsl-pure.ts` が出す、部品を返す関数(`diagram` を含む)を `located(fn)` で包む。包みは `Error.captureStackTrace` でスタックを取り、結果の部品に**列挙できるシンボルのキー** `SOURCE` で置く。整形はしない。行と桁は、読むときに初めて解く(D3)。
- 列挙できるシンボルなので、レイアウトの spread でも残る。JSON・`Object.keys`・SVG・PPTX には出ず、描いた結果は 1 バイトも変わらない。
- **既定では取らない。** CLI(`build` / `check` / `show` / `serve` / `notes`)が、ソースを読む前に `captureSourceLocations(true)` を呼ぶ。ライブラリとして使う人(`renderSpecEdge` を Workers で回す、ブラウザのページなど)には、手間も振る舞いの変化もない。ブラウザではスタックの書式が揃わないので、`captureStackTrace` がなければ何もしない。
- 部品の関数が中で別の部品の関数を呼んでも(`swimlane` が箱を作るなど)、中の呼び出しはパッケージの中のフレームなので、D3 で読み飛ばされ、利用者の呼び出しの位置になる。

**D3. どのフレームを位置にするか: 検査しているソースの中のいちばん内側の呼び出し。なければ利用者のファイルのいちばん内側の呼び出し。**
- svg-diagram のパッケージの中(パッケージの根より下)と `node:` のフレームは読み飛ばす。URL の `file://` と、読み直しのための問い合わせ(`?svg-diagram-fresh=…`、`lib/resolve-hook.ts`)は外す。
- 共通の部品を作る関数(`_parts.ts` の `card(x)` が `box()` を呼ぶ)を、ソースが何度も呼ぶ。このとき欲しいのは、ソースの中で `card(...)` を呼んだ行。だから**検査しているソースのフレームを先に探す**。ソースのフレームがないとき(部品を作ったのが別のファイルだけのとき)は、そのファイルの位置を返す。
- `Error.stackTraceLimit` は、包みの中だけ 30 に上げる。共通の部品が深く入れ子でも、ソースのフレームに届くように。

**D4. 指摘の位置を、その元から取る。**
- `build-error`: 投げた誤りの `stack` から D3 で取る。DSL が引数を拒んで投げた誤りでも、位置は利用者の呼び出しになる。
- 規則の指摘: `Finding` に `loc?: SourceLoc` を足す。部品を見て判定する規則は、その部品の `SOURCE` から取る。図全体を見る規則(幅・密度など)は `diagram()` の位置を使う。
- レイアウトの誤り: `Verdict` に `problemFindings: {message, loc?, related?}[]` を足す(`problems` の文字列は今のまま)。検査の四角(`CheckRect`)に、元の部品の `loc` を持たせる。2 つの部品の重なりは、1 つ目を `loc`、2 つ目を `related` にする。
- 位置を解けないとき(シンボルがない、スタックにソースのフレームがない)は、位置を付けない。今と同じに戻るだけで、誤った位置は出さない。

**D5. 出力の形。**
- `--format json`: 指摘に `line` / `column` を足す(位置が `file` の中のとき)。位置が別のファイルのときは `location: {file, line, column}` を足し、`file` は検査したソースのまま。重なりの相手は `related: [{file, line, column}]`。`--baseline` の指紋(`file`・`rule`・`message`)は変えない。行がずれても、ベースラインは外れない。
- `--format github`: `line=` / `col=` を足す。`--format sarif`: `region` と `relatedLocations`。
- `--format text`: `✗ src/a.ts:12:5: …`(ターミナルでクリックできる形)。
- `--worker`(並列の `--drift --rebuild`)が返すのは、解いたあとの普通の値だけにする。

**D6. 図からソースへ: SVG は変えず、別のファイルに地図を書く。** `build --locations FILE` は、レイアウトした部品ごとに `{loc, rect: {x, y, w, h}, label, node?}` を JSON で書く。`rect` は SVG の座標、`node` は ADR 0034 の名前。拡張のプレビューは、クリックの位置で四角を引いて、ソースへ飛ぶ。ソースのカーソルから図の部品を光らせるのも、同じ地図を逆に引けばよい。`reveal` の段は、地図に `reveal` / `until` を写す。

**D7. JSON の spec(MCP・デッキの `.json` の図)は、行ではなく JSON の場所(JSON Pointer)を位置にする。** `specToDiagram` が部品に `/parts/3` を置き、指摘は `path: "/parts/3"` を持つ。行と桁は、エディタが JSON を読んで出す(テキストを持っているのはエディタ)。これは U4 で、図のソースの位置(U1–U3)の後にする。

## 実装の順

- **U0**(この ADR): 位置がスタックで正しく取れること、費用、spread で残ることを確かめた(背景)。
- **U1**: `build-error` の位置(D3・D4 の最初・D5)。部品の包みは要らず、ここだけで拡張の後退が直る。`test/cli.test.ts` に、投げた行と、共通の部品から投げたときの位置を足す。
- **U2**: `located` の包みと `captureSourceLocations`(D2)。`partCatalog()` の全部品の例を組み立て、レイアウトのあとも全部の部品が `SOURCE` を持つことを、テストで確かめる。`rewrite` / `styled` / `mapBands` を通したあとも確かめる。包まれていない、部品を返す関数が公開の入口にあれば落ちるテストも足す。
- **U3**: 規則の指摘とレイアウトの誤りに位置を付ける(D4 の残り、D5)。拡張は、`line` があればそれを使い、なければ今のようにラベルを探す(古い core でも動く)。
- **U4**: `build --locations`(D6)と JSON の spec の場所(D7)。拡張のプレビューの「クリックでソースへ」と一緒に。

## 考えたが採らなかったこと

- **TypeScript でソースを読み、呼び出しを順に数えて部品に合わせる**: ループ・条件・共通の部品の関数があると、呼び出しの順と部品の順が合わない。実行して取るスタックなら、どう組み立てても呼んだ所が分かる。
- **部品に普通のフィールド(`src: '12:5'`)を足す**: 部品のキーを並べて読む所すべてに出てしまう。たとえば部品を `deepEqual` で比べるテスト(200 を超えるファイル)や、`rewrite` の patch。JSON の spec の部品とも形が変わる。
- **`WeakMap` で部品から位置を引く**: レイアウトが部品を spread で写すので、写したあとの部品からは引けない。
- **SVG に `data-src="12:5"` を書く**: ソースの行が変わるだけで SVG が変わり、ドリフトの検査(ADR 0038)が落ちる。地図は別のファイルにする(D6)。
- **すべての部品の関数の中で、それぞれ位置を取る**: 60 を超える関数を直すことになり、新しい部品で忘れやすい。入口で一度包む方が漏れない(U2 のテストで確かめる)。
- **`data.fix` から Quick Fix を作る**: `fix` は人が読む文で、機械が当てられる編集ではない。位置が入ったあと、別の ADR で決める。

## 結果

- 拡張の波線が、指摘の元の部品の行に付く。同じ文言の部品が 2 つあっても外れない。`build-error` は投げた行に戻る(0.8.0 での後退が直る)。
- CI の注釈(`github` / SARIF)が、PR の差分の行に付く。
- 描いた SVG・PPTX・JSON は変わらない(位置はシンボルのキーにあり、外に出るのは CLI の出力と `--locations` の地図だけ)。
- CLI の負担は、部品 1 つにつき数 µs。ライブラリとして使うと、既定では取らないので負担はない。
- 部品を足す人は、公開の入口から出せば包まれる(U2 のテストが見張る)。
