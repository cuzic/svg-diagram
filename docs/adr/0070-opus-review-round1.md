# ADR 0070 レビュー(第 1 巡、Opus)

## 結論(先に)

**方針は妥当、ただし Major 6 件を直してから承認。** Blocker 0・Major 6・Minor 8・Nit 3。

- 現状の実測は再現した(スクリプトを再実行: asap 2600×1700・折れ 116・4px 未満の並走 12 組 1175px、alap 2600×1767・折れ 54・並走 0・最小間隔 14px、`cause-crossing` は asap 2 件・alap 2 件で ADR の組と一致、u4 の口 703/725/747/769 と弧 693–731・741–779 も一致)。引用した file:line も、下の 1 件を除いて正しい。
- 診断(長い矢印の途中の曲がりが隙間の真ん中 `(p.x+q.x)/2` に集まる → 0px の重なり)は正しい。asap の 4px 未満の並走 15 区間を向き付きで出すと、**すべて隙間の中の水平の run** だった(層の中の run は 0)。D4 の狙いどころは合っている。
- alap に残る 2 つの `cause-crossing` の「推定」は、経路を出して確かめた(M2 の後の「補足」)。どちらも、縦の制約は循環せず、D4 の制約つき左端法で解ける。
- 直すべき点は、(1) D3/D4 の効く範囲の書き方が実際より狭い(pdpc・relationDiagram・whyWhyTree も同じ経路を通る)、(2) D4 の「構成上なくなる」を、後段(detour・D11〜D14・align)が壊しうる、(3) D3 の「単位」の定義では AND の無い入口まで広がる、(4) P1 の「縮小して見ると詰まる」が未決のまま、その却下の理由が既存の前例(`canvasGeom`)と合わない、(5) P3 の「弧と矢じりの重なり」を測っていない、(6) D1 で、役割の無い入口の節(未タグの根本原因)も上へ動く。

## 指摘

### Major

**M1. D3・D4 は `causeTree` だけでなく、pdpc・relationDiagram・whyWhyTree の出力も変える。「影響」と「完了の基準」が漏れている**
- 根拠: `pdpc`(`lib/dsl/diagrams.ts:471`)・`relationDiagram`・`whyWhyTree`(`:347`)はどれも `causeBand` を作り、`layoutCauseBand` → `tryLayoutCause` → `layeredAttempt`(`lib/toc.ts:278-279`)を通る。`groupOf` もここで**全 cause の帯に**渡している(`groupOf: k => groupIndex.get(k)`)。D4 の `tracks` を `toc.ts` から渡せば、これらにも効く。D3 も、下の M3 の定義のままだと、AND の無い pdpc の入口にも効く。ADR の「変わらない出力」は states・classes・semnet・bpmn だけを挙げ、D3 は「`groupOf` を渡す図(`causeTree`)だけ」と書いている。arrowDiagram は `StatesBand`(`:392`)なので D4 の範囲外で、ここは ADR の通り。
- 直し方: 次のどちらかを ADR に書く。(a) 有効にする条件を `band.base === undefined && band.layerFrom === undefined`(= `causeTree`)のように明記し、pdpc・relationDiagram・whyWhyTree は今の経路のままにする。(b) これらも対象にするなら、「影響」に挙げ、`examples/qc-pdpc`・`qc-relation` の golden の差分を U3・U4 の PR に載せる。pdpc の既定は `returns: 'outer'`(`:472`)で、外周の戻り辺の曲がり(`turnOuter`)を D4 の割り当てに入れる話と直に当たるので、(a) から始めるのが安全。

**M2. D4 の「同じ向きの run が `LANE` 未満で並ぶことは、構成上なくなる」は、後段の処理で崩れうる。後段との順序と採否の基準を決めていない**
- 根拠: 割り当ての後に経路を動かす処理が 5 つある。いずれも採否を「4px 未満の並走」(`runsTogether`、`lib/polyline-metrics.ts:111-117`)と (交差, 折れ) で判定しており、`LANE` 未満に近づくことは止めない。
  - `detour`: `causeTree` では既定で有効(`lib/toc.ts:279`)。探索した経路は `elbows` を通らずに置き換わる(`lib/layered-route.ts:258` `found ? [start, ...found.slice(1, -1), end] : elbows(...)`)。トラックを受け取る口が無い。
  - ADR 0016 D3 `align`(口の高さを動かす)。
  - D11 `sharing`(`laneShare`/`longLane`。長い矢印の最後の曲がりを先頭のレーンに置く、`:176-181`・`:254`)。
  - D12 `shiftOf`・D13 `turnAt`(曲がりを ±6/±14px 動かす、ADR 0016 D13)。
  - D14 `moveApart`(`:560-575`)。
  
  ADR は「`pick0`・`sharing`・`apartOf` は変えない」「D12〜D14 は残す」と書くだけで、`tracks` のときに D11 の `laneShare` が何を意味するか、detour の経路にトラックをどう当てるかを書いていない。
- 直し方: D4 に次の 3 点を足す。(1) `tracks` のとき、D11 の `laneShare`/`longLane` と `lastTurn` は割り当てに吸収して使わない。(2) detour の経路も、層の間の区間ではトラックの座標に合わせる。合わせられない場合は detour を採らない。(3) D12〜D14・align の採否に「`parallelRuns(routes, laneStepOf(space))` の合計が増えない」を足す。そのうえで U4 のテスト (1) を、detour が効く図(箱を避ける長い矢印)でも回す。

**M3. D3 の「組に入らない矢印は 1 本ずつを単位にする」では、AND の無い入口(OR の fan-in)まで口の間隔が 2〜4 倍になり、箱も広がる**
- 根拠: D3 の文言どおりなら、u3(AND 無し、入る矢印 3 本)は単位が 3 つで、口の間隔は 44〜88px、`need` は +44px になる。報告の図では e3・u3 がこれに当たり、`examples/` の CRT・FRT や pdpc では fan-in の大半がこれに当たる。一方で「影響」は「AND を持つ `causeTree` の図」としか書いていない。さらに、箱が広がると `maxNodeW: 'auto'` の幅の探索(`NARROWING`、ADR 0019 D2)や `fold` の判定が変わり、文字の折り返しまで動く図が出る。
- 直し方: 広げる間隔を「**AND の組と、それに隣り合う単位との間だけ**」にする。AND でない矢印どうしは今の `portStep` のままにする。`need` の追加も、(AND の組に接する境界の数)× `portStep` にする。U3 のテストに「AND の無い頭の口と箱の幅が変わらない」を足す。

**M4. P1(縮小して見ると 1〜数 px)を未決に回した理由が、既存の前例と合わない。完了の基準も、縮小して見たときの間隔を測っていない**
- 根拠: 「大きさの単位」の節は、文字が 1.29 倍で線の間隔が 1 倍のままであること、2600px の図を 0.38 倍で見ると 14px のレーンが 5px になることを、自分で示している。代替案の表は「`canvas.minText` の倍率で大きくすると、canvas を使うすべての図の出力が変わる」を理由に却下している。しかし、帯の種類ごとに canvas の倍率で幾何を大きくする仕組みは既にある(`canvasGeom`、`lib/layout-handlers.ts:603`。gantt・bars・chart・plane だけが使い、ほかの帯は不変)。`causeTree` には既に `env.space` の倍率の経路がある(`GAP`・`LEVEL`・`LANE`・`STUB` が `space` で変わる、`lib/toc.ts:278-279`)。また、D4 を入れても alap の最小間隔は 14px のままで、報告の図の見え方(0.38 倍で約 5px)はほぼ変わらない。
- 直し方: 新しい決定 D7 を立てる:「canvas のとき、cause の帯の `space` に `canvasGeom` を掛ける」。`PORT`・`AND_*` も同じ倍率にする(今の `portStep: PORT` は `space` で縮まない、`:279`)。canvas の無い図は不変なので、影響は canvas の cause 図に閉じる。実装の順番は U4 の後でよいが、未決ではなく決定にする。完了の基準には、「最小の並走の間隔 ÷ 文字の大きさ(`minText`)」のような**比**を足す。

**M5. P3 の「弧と矢じりが重なる」を測っていない。D3 で直るのは、2 つの弧の間の切れ目だけ**
- 根拠: 弧は先端から `AND_END = 21` の位置で始まり、制御点は `2×AND_PEAK − AND_END = 9`(`lib/toc.ts:29`・`:353`)なので、頂点は先端から約 15px になる。矢じりは長さ `ARROW_L = 12`・半幅 5(`lib/emit-common.ts:157`)。弧の頂点と矢じりの根元の間は約 3px しかなく、線幅 2 を引くと約 2px、0.38 倍の縮小では 1px 未満になる。ADR の表は「弧の x の範囲」と「弧どうしの切れ目」しか測っておらず、完了の基準も「切れ目 24px 以上」だけになっている。
- 直し方: 実測の表に「弧の頂点と矢じりの根元の距離」を足す。D3(または M4 の D7)で、`AND_END`・`AND_PEAK` を `ARROW_L` に対して決める(例: 頂点が根元から 6px 以上)と書く。完了の基準にもこの距離を足す。

**M6. D1 では、CRT の「役割の無い入口の節」(タグを付け忘れた根本原因)も上へ動く。ADR 0019 が CRT を asap に残した理由に、まだ当たる**
- 根拠: `alap` の動く節(movers)は「`keep` に無く、入る辺がすべて movers から来る節」(`lib/graph-layout.ts:369-381`)。`keep` は root・injection・start だけ(`lib/toc.ts:225`)。CRT の検査は root が 1 つ以上あることしか求めない(`lib/toc-rules.ts:35`)ので、入口の節に役割を付けない CRT は普通にある。`examples/toc-compact.ts` の `b3`(「見積もりが甘い」。中身は根本原因だが役割が無い)がその例で、この例では行き先が層 1 なので動かないが、行き先が深い図では動く。利用者の案 (d) は「**前提条件を**行き先の 1 つ下へ」で、ADR の「役割の無い入口の節とその連鎖」はそれより広い。なお報告の図は入口がすべて root か precondition なので、どちらの定義でも実測は同じになる。
- 直し方: `tree: 'crt'` の既定の ALAP では、`keep` を「入る辺の無い節のうち、`role !== 'precondition'` のもの」にする。動くのは前提条件とその連鎖だけになる。明示の `layer: 'alap'` は今の意味のままにする。U1 のテストに「役割の無い入口の節は CRT の既定で層 0 のまま」を足す。

### Minor

**m1. 「`test/` には `tree: 'crt'` が 9 ファイルに 25 か所」は 11 ファイル**
- 根拠: `grep -rc "tree: 'crt'" test` で 11 ファイル・25 行。toc・toc-fit・toc-rules・cause-hop・spec・spec-edge・keep-words・wrap-soft・diagnostics-hints・pptx-edge・pptx-groups。
- 直し方: 数を直し、U1 で見直すファイルを列挙する。

**m2. D4 で隙間の高さを全隙間で一律に広げる。`crowdOf` の数え方も変えると書いていない**
- 根拠: `corridorLoad` は全隙間の最大を 1 つ返し、`layoutWithLanes` はそれで `levelGap` を一律に決める(`lib/layered-route.ts:425`・`:434`)。長い矢印を数えると、混む 1 つの隙間のために図全体が高くなる。また、レーンの間隔 `laneIn` の分母になる `crowdOf`(`:114-123`)は長い矢印の曲がりを数えないので、トラックを増やしても間隔の計算が合わない。参考までに、報告の図で隙間ごとの水平の run の最大の重なり(区間グラフの密度。左端法の必要トラック数の下限)を数えると、asap・alap とも最大 3 で、`gapFor(3) = 80` は今の隙間(94・136)に収まる。この図では、高さは増えない見込み。
- 直し方: D4 に「`crowdOf` も同じトラック数で数える」と書く。`corridorLoad` を一律のまま使うのか、隙間ごとの `levelGap` にするのかも決める。後者は `graph-layout.ts` に手が入るので、別の単位にする。上の密度の実測を ADR の根拠に足す。

**m3. 左端法で同じトラックに並ぶ 2 本の run の端が近いと、1 本の線に見える**
- 根拠: D4 は「範囲が重ならない曲がりは同じトラックを使ってよい」と書く。端と端の間が数 px なら、別の矢印が 1 本につながって見える(P1 と同じ読み違い)。
- 直し方: 区間を両端で `laneStepOf(space)` ずつ伸ばしてから重なりを判定する。U4 のテストに 1 つ足す。

**m4. ADR 0028 の hop との関係を書いていない(`tree` を書いた CRT は既定で `hop: 'all'`)**
- 根拠: `tree` を書くと `hop: 'all'` が既定になる(`lib/dsl/diagrams.ts:294`)。hop は角から 8px 未満、隣の交差から 16px 未満、同じ向きの線が 10.5px 未満(`room = R + w/2 + 3`)のとき省かれる(`lib/cause-hop.ts:55-82`)。D4 でトラックの位置が変わると、飛び越す交差・省く交差の組が変わる。`density: 'compact'` のトラック間隔 11px は、hop の `parallel` の閾値(約 10.5px)の際に近い。
- 直し方: 「影響」に hop を足す。U4 の PR で、`toc-hop`・`toc-hop-all` の hop の数と、省いた理由ごとの内訳を before/after で出す。トラック間隔の下限を、hop の `room` より大きく保つと D4 に書く。

**m5. 完了の基準が、リポジトリに無い利用者のファイルに頼っている**
- 根拠: 完了の基準の 1 つ目は「報告の図(利用者のソース。リポジトリには入れない)」で測る。レビューする側も CI も確かめられない。
- 直し方: ラベルを伏せて構造だけ写した図(24 節・同じ link と AND・同じ役割、ラベルは同じ文字数のダミー)を `test/fixtures/` に置く。フォントに依らない基準(折れの最大 ≤ 4、`parallelRuns(·, laneStepOf())` = 0、AND の頭への交差 0、弧の切れ目 ≥ `2×portStep − 2×AND_REACH`)をテストにする。

**m6. U4 が大きすぎる。D4 の前提になる「推定」の確かめ方が、実装計画の表に無い**
- 根拠: U4 は、割り当て・制約・`elbows` の形・`corridorLoad`・`tracks` の口をまとめて 1 つにしている。「未決」は「U4 の前に小さな図で確かめる」と書くが、それをする単位が表に無い。
- 直し方: U4 を 3 つに分ける。U4a: 長い矢印の途中の曲がりにトラックを割り当てる(真ん中の重なりを消す。P1 の主因)。U4b: 縦の制約で `fanIn` の分岐を置き換える(交差 2 件)。U4c: `corridorLoad`・`crowdOf`。推定の確認は U4b の最初のテストにする(下の「補足」のとおり、どちらも制約は循環しない)。

**m7. D2 の `edge-parallel` が、`portStep` の短い図で誤検知しやすい**
- 根拠: states・classes の `portStep` の既定は 14 で、面が短いと `min(portStep, (h−12)/(n−1))` まで縮む(`lib/layered-route.ts:155`)。D2 の `sep = 14` だと、fan-in の最後の run どうしが常に該当する。`routedBands` には chart の網の図(pert・dependency)も入る(`lib/rules.ts:655`)。
- 直し方: 「未決」の「多ければ cause の帯に限る」を、最初から cause の帯に限る形に改める。広げるのは U5 の測り直しの後にする。

**m8. D3 で口を面の幅へ広げると、ダミーの列(箱の中央)と口がずれ、最後の隙間で段差が 1 つ増える**
- 根拠: 長い矢印の最後のダミーは BK で箱の中央の列に寄る。口を中央から ±55px まで広げると、`elbows` の最後の区間で横の run が増える。報告の図の alap にも、pre3→u4 に 7px の段差(718→725)が既にある。
- 直し方: 広げる上限を「面の幅」ではなく `2 × portStep` に固定する(弧の切れ目 24px は満たす)。広げる場合は、U3 の完了の条件に「折れの合計が増えない」を足す。

### Nit

- n1. 「並走」の定義が、現状の節では「同じ向きの run」、D2 では「同じ向き」と書いてあり、向き(水平・垂直)なのか進む向き(矢印の向き)なのかが曖昧。測定スクリプトは水平・垂直だけで判定している。「同じ軸の run」と書く。
- n2. D1 の `examples/toc-compact` の推定は、`b3` だけでなく連鎖の `a3`(入る辺が `b3` だけ)も動く候補になる。結果は同じ(`a3` の行き先 `a5` が層 2 なので層 1 のまま)だが、推定の書き方を直す。
- n3. 「`pick0`(並びの再探索を含め 28 回以上)」の数は、再現の手順(一時的なログ)を PR 本文に 1 行で書いておくと、U5 で測り直しやすい。

### 補足: alap に残る 2 つの交差の確認(未決の「推定」)

経路を出して確かめた(alap、図の座標。`dir: 'up'` なので、y が小さいほど頭に近い)。

- u4: `u3→u4` は `1260,525 → 1260,465 → 769,465 → 769,377`、`pre4→u4` は `990,525 → 990,437 → 747,437 → 747,377`。u3 の水平の run(y = 465、x = 769〜1260)が、pre4 の縦の run(x = 990)を横切っている。制約は 2 つあり、どちらも同じ向きを求める: pre4 の尾の列 990 が u3 の区間に入るので、pre4 を尾の側にする。u3 の頭の列 769 が pre4 の区間に入るので、u3 を頭の側にする。循環は無い。今は逆(pre4 が 437、u3 が 465)で、ADR の「fan-out の順になる」という読みと合う。
- e2: `r1→e2` の最後の曲がりは y = 1121(頭の近く、`lastTurn`)、`pre1→e2` の曲がりは y = 1213(尾の近く)。制約は「pre1 を頭の側、r1 を尾の側」で、これも循環は無い。

どちらも、D4 の制約つき左端法で交差 0 にできる。「未決」から外して、U4b のテストの期待値にしてよい。

## 判定

**要修正(Major 6 件)。** M1〜M6 を ADR に反映した版で第 2 巡を行う。D1(U1)は M6 を反映すれば先に実装してよい。D2・D5・D6 の方向は承認する。
