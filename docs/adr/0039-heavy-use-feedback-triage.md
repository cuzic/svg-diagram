# ADR 0039: 大量利用の報告にもとづく改修依頼 14 項目の仕分けと順序

- 状態: 提案(方針のみ。各項目は別 PR で、必要なら個別の ADR を足す)
- 日付: 2026-10-21
- 基点: `main`(PR #312 まで)
- 関連: ADR 0037(別の大量利用の報告にもとづく診断改善。同じ種類の依頼)、ADR 0038(`check --drift --rebuild` の並列とキャッシュ)、ADR 0019(`maxNodeW`・`dir: 'auto'`)、ADR 0015(TOC の `tocCheck`)
- 由来: 書籍原稿の制作で、画像生成 AI が作った PNG 約 250 枚の SVG への置き換えと、章ごとの TOC 図約 100 枚を、並列エージェント約 26 本で作った利用者の報告(別セッションから受領)

## 背景

依頼は 14 項目。性質が違うので、ひとまとめに実装せず、**既にあるもので足りる / 小さい修正 / 新機能 / 運用の説明**に分ける。確認した事実:

- 項目 1: 再現した。原因は型定義の解決ではなく、報告者のプロジェクトに `node_modules/.bin` がなく **`tsc` が見つからない**こと(`typescript が見つからない` で止まる)。`svg-diagram` の symlink 自体は、typecheck の `paths` 補完で解決できる。
- 項目 2: 型検査が通れば `banner({text})` は TS エラーになる(確認済み)。実行時の未知キー検出は、部品ごとのキー一覧が無い(型にしか無い)ので、機械的には入らない。
- 項目 3: PR #312 で `diff --text` に「網羅」モードが入った。PNG 入力(OCR)は無い。
- 項目 6: README 記載のとおり `keepWords` は `cycle` / `chevron` / `swimlane` / `cloud` に効かない。
- 項目 13: `--jobs` と成功キャッシュは `check --drift --rebuild` にだけある(ADR 0038)。

## 決定

### D1: 小さい修正を先に出す(1 PR ずつ)

| 項目 | 内容 |
|---|---|
| 1 | `typecheck` は、プロジェクトにも PATH にも typescript が無いとき、svg-diagram 自身の typescript を使う(**実装済み**)。`init` の最後の案内も「typescript を入れる」から「`svg-diagram typecheck` で足りる」へ寄せる |
| 2 | 型検査が効くことを `init` の案内と README に書く。実行時の未知キー検出は **`banner` / `box` など使用頻度の高い部品から、受け付けるキーの一覧を 1 か所に持たせて throw** する(一覧は型から生成する検査 = テストで型とずれたら落とす)。全部品の一括導入はしない |
| 5 | `diagram({title, showTitle: true})`: 題名を図の先頭の見出しとして描く。既定 off(書かなければ SVG は 1 バイトも変わらない)。`caption()` は残す |
| 10 | `diagram({partial: true})`: 部分図の宣言。`toc-ude-count` / `toc-no-desired-result` と、AND の合流による `cause-crossing` を info に下げる。`.svg-diagram.json` のパス別 accept は **見送り**(書き方の設計が要る。`partial` で、全 CRT に同じ accept を書く手間は消える) |
| 13 | 並列利用の注意を README に書く(`build` は引数のソースだけを触る / glob の展開は呼び出し側 / 書いたファイルを 1 行ずつ出す。既に出ていれば現状維持)。`check --strict` への `--jobs` と成功キャッシュは ADR 0038 の仕組みを流用できるか **調べてから** 決める |

### D2: 新機能は、依頼者の実ファイルで再現してから設計する(各項目で個別に ADR 化するかを決める)

- **項目 4(`math()` の日本語)**: 数式は MathJax の輪郭で描いている(PR #146)。CJK を輪郭に載せるには日本語フォントが要り、`\text{}` の中の CJK だけ通常の文字描画に出す案が筋。`fraction(num, den)` を別部品にするより、**`math()` の `\text{…}` に日本語を許す**ほうが TeX の書き方と揃う。上付き(「経過年数乗」)も同じ経路。設計は、日本語の分子・分母を持つ縦書きの分数(報告で再現できなかった 1 枚)を再現の基準にする。
- **項目 3(PNG との文言照合)**: OCR は外部コマンド(`tesseract`、jpn)を**任意依存**として呼ぶ。未導入なら案内を出して終了コード 2。信頼度が低い語は「要目視」の別枠。`diff --text` の網羅モード(#312)の入力に「OCR した語の一覧」を足す形にして、照合の本体は共有する。OCR 精度は、崩れた文字を含む実際の画像で実測してから、閾値の既定を決める。
- **項目 6(`cycle` の語割れ・溢れ)**: `keepWords` を `cycle` / `chevron` に効かせるには、枠が先に決まる作りを、文字から枠を決める順に変える必要がある。**`cycle` だけ**先に直す(円の径を最長の語から決める。3 つの円が幅に収まらないときは、円を縮めずに警告 `cycle-overflow`)。
- **項目 7(行をまたぐ戻り矢印)**: `causeTree` / `stateDiagram` の `returns: 'outer'` と同じ外周レーンを `steps` / `row` に持ち込む。`connect()` の経路探索が箱を避けられないことが根本原因なら、そちらを直すほうが他の図にも効く。先に、報告された再現ファイルで、なぜ他の箱に重なるかを調べる。
- **項目 8(矢印ラベルの重なり)**: 短い矢印のラベルを矢印の脇に避けるモード。`connect(label)` の配置規則(ADR 0035 付近の経路)を読んでから、報告された再現 3 例で測る。
- **項目 9(`flowchart`)**: process / decision / terminator の軽量部品。BPMN との違いを README で説明できるか(重複にならないか)を **Opus レビューで確認してから** 着手する。
- **項目 11(`kind: 'form'`)**: 用途プリセット。`density`(`check` の rule)と `gray-tone-collision` の閾値を緩める。プリセットの名前と範囲(他の `kind` を将来足すか)を決めてから。ADR 0036 の `density`(間隔)と**名前が衝突しない**ようにする(rule 名の `density` と `diagram({density})` は別物)。
- **項目 12(縦長)**: `check` の info `aspect-extreme`(縦横比が閾値を超え、`fold` を使っていないとき、`fold` または分割を勧める)。自動で `fold` にはしない(図の見え方が黙って変わるため)。

### D3: 運用の改修で足りるもの

- **項目 14(`--fix-refs`)**: `check --docs` が「参照先の PNG が無く、同名の SVG がある」を検出して**差し替え案を出す**ところまで先に。`--fix-refs` による書き換えは、`--dry-run` と差分表示を付けた次の PR。

### D4: 順序

1. D1 の項目 1(実装済み)→ 2 → 5 → 10 → 13(いずれも小さく、報告者の次の改訂に直接効く)
2. 項目 4 → 3(依頼者が「次の改訂に効く」とした 1〜5 のうち、残る 2 つ)
3. 項目 6 → 7 → 8(図の描画の品質。再現してから)
4. 項目 11 → 12 → 14 → 9

## 結果として

- 報告者側は、項目 1 の修正だけで、`typecheck` が走り、既存図の型エラー(`solid-danger`、`align: 'end'`、同名キー重複など)が見える。これは**図が変わる修正が必要**になるので、報告者側の対応が要る。
- 項目 2 の「全部品の未知キー検出」は、やらない。型検査で足りるものを実行時にも二重に持つと、型とずれたときに両方を直す負担が増える。使用頻度の高い部品だけに絞る。

## 未決

- 項目 9 を部品として足すか、BPMN の軽量プリセットとして足すか。
